0) First: the hard truth about “invisible on GitHub”


0.1 “Invisible repo”

- Public repo cannot be invisible. If it’s public, people can find it, clone it, fork it.
- The only real protection is: make the repository Private.


0.2 “Invisible website”

- GitHub Pages is fundamentally public hosting. If someone has the URL, they can access it.
- You can discourage indexing (robots.txt), but that does not prevent access or copying.
- Also: even if the repo is private, if your site is public, users can still download the built JS/HTML from the browser (not your source repo, but the shipped artifact). There is no perfect “no download” for frontend code delivered to browsers.

So the practical choices are:


Option A (Best “hide code”): Private repo + deploy somewhere else

- Keep code private
- Host publicly on Vercel/Netlify/Cloudflare Pages (repo private supported), or even GitHub Pages via CI push to a public “deploy” repo (explained below)


Option B (Best “hide site”): Put the site behind authentication

- GitHub Pages does not support password protection natively.
- Use Cloudflare Access / Netlify password / Vercel protection / a simple auth proxy.


Option C (If you insist GitHub Pages): accept site is public

- You can still keep repo private depending on GitHub plan (next section).

2) “No trouble” hosting plan (staged) — works for React/Vite-style builds

I’ll give a robust baseline that prevents 80% of common failures.


Stage 1 — Make npm installs deterministic (stops “works on my machine”)

Goal: same Node/npm versions everywhere (your laptop + GitHub Actions).

- Check Node version locally:

```
Bashnode -v
npm -v
```

- Add an engines pin (prevents random CI breakage):

```
jsonc// package.json (add incrementally)
{
  "engines": {
    "node": ">=20"
  }
}
```

- Always use `npm ci` in CI (not `npm install`).

- `npm ci` respects your lockfile strictly and is far more stable.

Common real-world failure this prevents: peer dependency drift, random lockfile regeneration, CI-only build breaks.


Stage 2 — Make GitHub Pages pathing correct (the #1 “blank page” cause)

You must set the correct “base path” depending on your toolchain.


If you use Vite (most modern React setups)

Add base in `vite.config.ts/js`:

```
TypeScript// vite.config.ts (incremental change)
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  base: "/YOUR_REPO_NAME/", // critical for GitHub Pages
});
```


If you use CRA (Create React App)

Add homepage:

```
jsonc// package.json (incremental change)
{
  "homepage": "https://YOUR_GH_USERNAME.github.io/YOUR_REPO_NAME/"
}
```

Why this matters: GitHub Pages serves your app under `/repo-name/`. Without base/homepage, your app requests `/assets/...` from root and fails.


Stage 3 — Fix routing so refresh doesn’t 404 (critical on Pages)

GitHub Pages cannot rewrite routes like a real server.


The simplest fix (recommended): HashRouter

In your app routing:

```
React// Stage 3 change: use HashRouter
import { HashRouter } from "react-router-dom";

export function AppRoot() {
  return (
    <HashRouter>
      {/* your Routes here */}
    </HashRouter>
  );
}
```

QA note: HashRouter is the “lowest support cost” choice for static hosting.


If you refuse HashRouter (BrowserRouter)

You’ll need a 404 fallback trick (more brittle). I can provide it, but HashRouter is the stable enterprise answer for Pages.


Stage 4 — Deploy with GitHub Actions (removes “npm run deploy” pain)

This avoids local deploy differences and “works locally only”.


Step 4.1: Add a build script (if missing)

```
jsonc// package.json (incremental check)
{
  "scripts": {
    "build": "vite build"
  }
}
```


Step 4.2: Add workflow (Vite outputs to dist)

Create: `.github/workflows/pages.yml`

```
YAML# Stage 4: minimal, stable pipeline (incremental)
name: Deploy to GitHub Pages
on:
  push:
    branches: [ "main" ]

permissions:
  contents: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: "npm"

      - run: npm ci
      - run: npm run build

      # Vite output folder is typically "dist"
      - uses: JamesIves/github-pages-deploy-action@v4
        with:
          branch: gh-pages
          folder: dist
```

If your build output is `build` (CRA), change `folder: build`.

Stage 4 QA gate: After push, check Actions logs end-to-end. If it passes, Pages should update.


Stage 5 — Prevent Jekyll from breaking asset folders (edge case but real)

Some filenames can get treated weirdly by Pages’ Jekyll pipeline.

Add an empty file:

- `public/.nojekyll` (or in build output root depending on your setup)

For Vite, you can place `.nojekyll` in `public/` so it copies into `dist/`.


3) Keeping your project “hidden” while still deploying

Now the “invisible” part—realistic options.


Option 1 (Best): Private repo + paid GitHub plan that supports Pages from private repo

- Repo stays private
- Site can still be public
- People can’t clone your source repo


Option 2 (Works on Free): Two-repo “source private → deploy public”

- Repo A (private): your real source code
- Repo B (public): contains only built `/dist` (deployment artifact)
- GitHub Action in Repo A pushes build to Repo B

This hides source code but not the built app (still viewable in browser).

If you want, I’ll walk you through this pattern step-by-step next (it’s a bit longer, but very doable).


Option 3: Make the site private (requires non-GitHub Pages protection)

If the goal is “people can’t even access the site”, use:

- Cloudflare Access (password/SSO gate)
- Netlify/Vercel protected deployments
- Basic-auth proxy in front of static hosting

GitHub Pages alone can’t do this properly.


4) “All the real problems when hosting” + fixes (QA-style checklist)

Below are the issues that repeatedly happen, plus what to do.


4.1 Install / npm problems

-

`npm ci` fails with ERESOLVE / peer deps

  - Fix: upgrade conflicting packages; as a temporary workaround:

```
Bashnpm ci --legacy-peer-deps
```

  - QA note: treat legacy-peer-deps as temporary, not permanent.
-

Node version mismatch

  - Fix: pin Node in Actions (`setup-node@v4 node-version: 20`) and optionally add `.nvmrc`.
-

Lockfile corruption / inconsistent installs

  - Fix:

```
Bashrm -rf node_modules package-lock.json
npm install
```

  - Then commit the new lockfile once it’s stable.


4.2 Build / runtime problems

-

Blank page after deploy

  - Cause: wrong base/homepage.
  - Fix: set Vite `base: "/repo/"` or CRA `homepage`.
-

Routes work until refresh → 404

  - Fix: HashRouter.
-

Assets 404 (images/CSS/JS not found)

  - Fix: base/homepage + avoid root-absolute paths like `/assets/x.png`; prefer relative or import-based assets.
-

Case sensitivity differences

  - Works on Windows/macOS, fails on Linux (GitHub Actions).
  - Fix: ensure imports match exact file casing.


4.3 GitHub Pages / Actions problems

-

Workflow passes but Pages not updated

  - Fix: Repo Settings → Actions → Workflow permissions → set to Read and write.
-

Deploy action says it pushed but site still old

  - Fix: browser cache + wait a few minutes + confirm Pages is set to `gh-pages` branch.
-

404 on site root

- Fix: correct URL is `https://USERNAME.github.io/REPO/` (not just username domain unless it’s a user/org site repo).


4.4 Security / “don’t leak secrets”

- Accidentally committed `.env`

- Fix: rotate keys immediately; add `.env` to `.gitignore`; use GitHub Secrets for CI.

- Users can “download your app”

- Reality: any public web app can be downloaded as built assets.
- Mitigation: keep proprietary logic server-side (serverless API), not in frontend.
